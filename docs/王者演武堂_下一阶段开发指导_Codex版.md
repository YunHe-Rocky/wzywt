# 王者演武堂：下一阶段开发指导（Codex 版）

> 用途：交给 Codex / 开发智能体直接阅读并按现有项目架构实施。  
> 核心目标：在不破坏现有分队、赛事、权限、安全与部署体系的前提下，把王者演武堂从“分队工具”继续扩展为完整的内战记录平台。

---

## 0. 本文档的最高优先级规则

本次开发以以下业务链路为主：

**分队 → 队内战术规划 → 内战 → 上传赛后战绩 → 保存比赛档案 → 精彩视频与互动沉淀**

Codex 开发时必须遵守：

1. **先阅读现有代码和架构文档，再修改。**
2. **不得因为本次功能新增而重写整个项目。**
3. **不得创建 `Phase1`、`Phase2`、`Phase-A`、`阶段1`、`阶段2` 等以开发阶段命名的代码目录。**
4. 新代码必须进入现有业务领域和项目既有架构中，例如已有的：
   - `src/core`
   - `src/lib`
   - `src/app`
   - `src/web`
   - `src/server`
   - `prisma`
   - `tests`

   具体放置位置以仓库当前实际结构为准，**禁止为了“开发阶段”污染目录结构**。
5. 如仓库已有等价模块、Service、Repository、Storage、权限函数、审计机制，应优先复用或扩展，**不得平行再造第二套体系**。
6. 不允许静默改变既有业务规则。
7. 每一次修改都必须做到：
   - 可运行；
   - 可测试；
   - 可回退；
   - 有明确修改文件；
   - 有真实测试结果。
8. 不得为了让 CI 通过而：
   - 删除测试；
   - 关闭规则；
   - 永久 `continue-on-error`；
   - 大量使用 `any`；
   - 绕过 TypeScript；
   - 吞掉异常。
9. `src/core` 如当前定义为纯函数层，必须继续保持纯函数边界，不得引入 Prisma、Next.js、React、Redis、网络 I/O。
10. 遇到本文档没有明确的新问题时，优先保持现有业务行为；若现有实现与本文档明确业务规则冲突，以本文档为准。

# 1. 产品范围

本轮主要增加三个业务域：

1. **内战战绩记录**
2. **演武动态 / 成员击杀剪辑墙**
3. **队内战术室**

同时要求把一场内战从“分队结果”扩展成可以永久保存的完整比赛档案。

---

# 2. 一场完整内战最终需要保存什么

| 阶段 | 需要保存的内容 |
|---|---|
| 分队 | 红蓝双方正式成员、补位成员、位置分配 |
| 阵容 | 双方本局实际使用英雄 |
| 战术 | 红蓝双方独立战术室、战术图层、成员路线、点位、文字说明 |
| 比赛 | 比赛时间、胜负、双方总击杀等基础结果 |
| 战绩 | 双方 10 名玩家完整赛后数据 |
| 原始资料 | 数据、输出、生存、发育、战绩、团队 6 张原始截图 |
| 精彩内容 | 与本场比赛关联的视频动态、点赞、评论 |

这些数据属于历史比赛档案，**不能因为赛事结束、房间关闭或后续重新分队而自动删除**。

# 3. 内战战绩记录

## 3.1 上传权限

每场内战结束后，可以上传赛后战绩的人：

| 身份 | 上传战绩 | 确认玩家归属 | 修改正式战绩 | 提出异议 |
|---|---:|---:|---:|---:|
| 普通成员 | × | × | × | ✓ |
| 房主 | ✓ | ✓ | × | ✓ |
| 次房主 | ✓ | ✓ | × | ✓ |
| 超级管理员 | ✓ | ✓ | ✓ | ✓ |

规则：

- 房主、次房主、超级管理员均可上传。
- 房主和次房主可以进行玩家归属确认。
- 正式入库后的最终数据修改权只属于超级管理员。
- 普通成员不能直接修改正式比赛数据，只能提出异议。
- 超级管理员纠错必须有完整审计记录。

---

## 3.2 第一版固定上传 6 张截图

第一版只处理以下 6 个王者荣耀赛后栏目：

| 序号 | 截图页面 | 需要读取的数据 |
|---:|---|---|
| 1 | 数据 | 输出伤害、承受伤害、总经济、参团率 |
| 2 | 输出 | 输出伤害、伤害转化比 |
| 3 | 生存 | 承受伤害、每死承伤 |
| 4 | 发育 | 总经济、野怪经济、补刀数 |
| 5 | 战绩 | 击败、死亡、助攻（K / D / A） |
| 6 | 团队 | 参团率、控制效果、治疗量、对塔伤害 |

标准截图组：

**数据 + 输出 + 生存 + 发育 + 战绩 + 团队 = 6 张**

### 第一版明确不做

- 不上传“总览”页；
- 不识别“总览”页；
- 不上传“表现”页；
- 不识别“表现”页；
- 不要因为评分字段存在就额外增加第 7 张截图。

## 3.3 六张截图的具体含义

六张截图不是六场比赛，也不是只截单个玩家。

每一张都必须：

- 来自**同一场比赛**；
- 完整显示红方 5 人；
- 完整显示蓝方 5 人；
- 总计显示双方 10 名玩家；
- 昵称清晰；
- 英雄清晰；
- 评分清晰；
- 对应栏目数据清晰；
- 不得裁掉关键区域。

六张截图分别用于：

### 截图 1：数据

用于读取：

- 输出伤害；
- 承受伤害；
- 总经济；
- 参团率。

### 截图 2：输出

用于读取：

- 输出伤害；
- 伤害转化比。

### 截图 3：生存

用于读取：

- 承受伤害；
- 每死承伤。

### 截图 4：发育

用于读取：

- 总经济；
- 野怪经济；
- 补刀数。

### 截图 5：战绩

用于读取：

- 击败；
- 死亡；
- 助攻。

### 截图 6：团队

用于读取：

- 参团率；
- 控制效果；
- 治疗量；
- 对塔伤害。

---

## 3.4 评分的处理

“评分”属于每名玩家的正式战绩字段，但**不是单独的一张截图页面**。

需要保存：

- 每名玩家本场评分。

原则：

- 能从六张截图中稳定识别时直接进入识别结果；
- OCR 结果必须允许上传者在正式提交前人工核对；
- 不允许因为 OCR 无法确认评分而伪造默认值；
- 未确认字段必须明确标记为“待确认”；
- 正式提交时若评分属于必填字段，则必须先人工补齐。

---

## 3.5 重复指标只保存一份

以下字段会在不同截图页面重复：

- 输出伤害；
- 承受伤害；
- 总经济；
- 参团率。

数据库中：

**同一名玩家、同一场比赛、同一指标只保存一个正式值。**

前端可以为了保持王者荣耀原本的浏览习惯，在多个栏目重复显示同一个值，但不允许数据库创建多份互相可能冲突的数据副本。

# 4. 截图上传与识别流程

完整流程建议固定为：

```text
选择比赛
  ↓
上传 6 张固定栏目截图
  ↓
服务器保存原图
  ↓
校验图片类型 / 数量 / 清晰度基础信息
  ↓
识别双方 10 名玩家、英雄、评分、栏目数据
  ↓
跨 6 图进行同场一致性校验
  ↓
合并重复字段
  ↓
根据英雄 + 可能分路 + 当前分队成员做玩家归属推荐
  ↓
房主 / 次房主人工确认玩家归属
  ↓
人工检查 OCR 数据
  ↓
正式提交
  ↓
生成不可静默覆盖的正式比赛档案
```

---

# 5. 同场一致性校验

系统必须尽可能校验六张图是否属于同一场比赛。

至少检查：

- 红蓝双方人数；
- 双方玩家昵称；
- 双方英雄；
- 红蓝阵营顺序；
- 比分 / 总击杀（如果页面可读取）；
- 重复字段在多个截图中的数值是否一致；
- 同一英雄是否在多张图中出现位置明显错乱。

校验结果至少分为：

- `PASS`：高度一致；
- `WARNING`：存在疑点，可以人工检查；
- `FAIL`：明显不是同一场或关键数据缺失，不允许直接正式提交。

不得因为 OCR 某一个字符识别错误就直接判定整组截图失败。

应优先使用：

- 归一化昵称；
- 模糊匹配；
- 多图交叉验证；
- 英雄组合；
- 阵营位置；

综合判断。

---

# 6. 玩家身份确认

系统不能因为“识别到某个英雄”就直接认定是哪名网站成员。

原因：

- 同一英雄可能走多个分路；
- 成员也可能临时换位置；
- 实际比赛阵容可能与赛前预期不同；
- 可能存在补位玩家。

正确流程：

```text
识别英雄
  ↓
推测可能分路
  ↓
结合本场当前分队成员
  ↓
结合成员原本位置偏好 / 常用英雄（若已有）
  ↓
给出推荐匹配
  ↓
房主 / 次房主人工确认
  ↓
正式绑定
```

### 关键限制

- 系统只做**辅助推荐**；
- 不允许自动认定最终玩家身份；
- 房主 / 次房主确认后才能正式入库；
- 超管拥有最终纠错权。

# 7. 补位 / 非本站成员

如果本局有不是本站正式成员的人：

- 标记为“补位 / 非本站成员”；
- 保存其本场：
  - 昵称；
  - 英雄；
  - 阵营；
  - 分路；
  - 评分；
  - KDA；
  - 输出；
  - 承伤；
  - 经济；
  - 团队数据；
  - 其他本局字段；
- 数据属于本场比赛档案；
- **不得累计进任何正式网站成员个人档案**；
- 后续如果该玩家注册网站，也不能无审核地自动把历史补位数据合并到新账号。

# 8. 战绩正式提交后的可见性

正式提交以后：

- 网站成员可以查看红蓝双方完整比赛战绩；
- 不只本队可见；
- 红队可以看蓝队赛后数据；
- 蓝队可以看红队赛后数据。

需要明确区分：

### 赛前 / 赛中战术

属于队内私有内容。

- 红方看不到蓝方战术；
- 蓝方看不到红方战术。

### 赛后战绩

属于公共比赛档案。

- 双方成员均可查看；
- 按权限规则决定是否允许游客查看，第一版至少要求登录成员可查看。

# 12. 原始截图永久保存

六张原始截图属于比赛证据资料。

必须：

- 永久保存；
- 与比赛 ID 关联；
- 保存截图类型；
- 保存上传者；
- 保存上传时间；
- 保存文件哈希；
- 保存文件大小；
- 保存 MIME；
- 支持超管查看原始截图；
- 数据纠纷时可以追溯。

删除比赛时如产品未来允许删除，原始截图也必须遵循明确的数据删除策略，不能出现数据库删了但磁盘长期残留的孤儿文件。

# 13. 建议的数据模型

> 以下为逻辑模型。Codex 必须先检查现有 Prisma Schema / 数据模型，如已有 `Tournament`、`SplitResult`、`Member`、`User`、`AdminOperation` 等模型，应复用关系，不得创建重复概念。

## 13.1 Match / InternalMatch

代表一场真实完成的内战。

建议字段：

```text
id
tournamentId / roomId / splitId
playedAt
status
winnerSide
redTotalKills
blueTotalKills
createdBy
createdAt
submittedAt
submittedBy
updatedAt
```

状态至少能区分：

```text
DRAFT
UPLOADED
RECOGNIZED
WAITING_CONFIRMATION
SUBMITTED
```

如项目已有状态规范，使用项目现有命名。

---

## 13.2 MatchPlayer

表示某场比赛中的一个玩家槽位。

建议字段：

```text
id
matchId
side
slot
memberId nullable
isGuest
gameNickname
heroId / heroName
role
score
isWinner
createdAt
updatedAt
```

要求：

- 每场正式比赛最终正好 10 条；
- 红 5、蓝 5；
- `memberId` 对补位可为空；
- `gameNickname` 必须保存，不能只依赖网站昵称；
- `hero` 保存应优先关联项目已有英雄数据源；
- `role` 使用项目已有分路枚举。

---

## 13.3 MatchPlayerStat

逻辑上保存每名玩家本场唯一指标。

字段示例：

```text
matchPlayerId

damageDealt
damageTaken
gold
participationRate

damageConversionRate
damageTakenPerDeath

jungleGold
minionKills

kills
deaths
assists

controlScore
healing
towerDamage
```

### 数据类型要求

百分比：

- 不要保存 `"42.5%"` 这种展示字符串；
- 应保存标准数值；
- 前端负责格式化。

大整数：

- 伤害、经济、治疗、推塔伤害等要考虑数值范围；
- 选择能覆盖未来数值范围的数据库类型。

缺失值：

- OCR 未识别 ≠ 0；
- 必须允许区分：
  - 真正为 0；
  - 未识别；
  - 未确认。

# 14. 数据库约束与索引

至少考虑：

### 唯一约束

- 一场比赛同一 `side + slot` 只能有一个 MatchPlayer；
- 一名 MatchPlayer 只能有一份正式 Stat；
- 一场比赛同一 screenshot `type` 第一版只能有一张当前有效原图；
- 防止正式比赛重复提交。

### 索引

建议覆盖常用查询：

- `match.tournamentId`
- `match.playedAt`
- `match.status`
- `matchPlayer.matchId`
- `matchPlayer.memberId`
- `matchPlayer.heroId`
- `matchScreenshot.matchId`
- `matchScreenshot.type`
- `dispute.matchId`
- `dispute.status`

不要为了“看起来完整”盲目给每个字段建索引。

# 15. Migration 规则

Codex 可以：

- 修改 `schema.prisma`；
- 创建新的 migration；
- 在本地测试 migration；
- 运行 `prisma validate`；
- 运行 `prisma generate`。

Codex 不得：

- 删除已有 migration；
- 重写已经进入历史的 migration；
- 在生产环境使用 `prisma db push` 替代正式 migration；
- 假装已经在生产执行 migration。

生产 migration 必须在最终交付报告中列为**人工执行事项**。

# 18. API 错误语义

至少区分：

- `401 Unauthorized`
- `403 Forbidden`
- `400 Validation Error`
- `404 Not Found`
- `409 Conflict`
- `413 Payload Too Large`
- `415 Unsupported Media Type`
- `422 Recognition / Business Validation Failure`
- `429 Too Many Requests`

# 24. 视频存储要求

第一版允许存本机服务器，但代码不能与本机路径强耦合。

需要抽象类似：

```ts
interface MediaStorage {
  save(...)
  open(...)
  delete(...)
  exists(...)
}
```

名称按项目规范调整。

以后迁移到：

- S3；
- OSS；
- COS；
- MinIO；
- 其他对象存储；

时不应重写业务层。

### 严禁

把真实视频目录直接挂成：

```text
/public/videos/xxx.mp4
```

然后任何人拿到链接就能绕过登录。

正确方式：

- 数据库保存 storage key；
- 请求播放时先鉴权；
- 再由受控 Route / Controller 返回文件或短效授权地址；
- 支持 Range 请求，避免视频在线播放必须整文件下载。

# 25. 上传安全

- 登录状态；
- 业务权限；
- 文件数量；
- 文件大小；
- MIME；
- 扩展名；
- 实际文件类型；
- 文件名净化；
- 路径穿越；
- 随机 / 哈希存储键；
- 重复文件；
- 空文件；
- 超限文件。

例如不能：

# 27. 战术路线权限

每队 5 名成员使用固定颜色。

规则：

| 能力 | 成员 |
|---|---|
| 查看本队其他 4 人路线 | ✓ |
| 创建自己的路线 | ✓ |
| 修改自己的路线 | ✓ |
| 删除自己的路线 | ✓ |
| 修改队友路线 | × |
| 删除队友路线 | × |
| 帮队友画路线 | × |

**特别强调：不能帮队友画路线。**

不能仅做：

```ts
if (isSameTeam) allowEdit()
```

```text
当前用户 == route.owner
```

示例：

- 掉一塔后；

每个图层可以保存：

- 名称；
- 排序；
- 可选时间范围；
- 战术说明；
- 5 名成员路线；
- 点位；
- 简单文字。

# 36. 安全要求

本功能必须继续遵守项目现有安全规则。

### Session

- 不自行新建第二套登录态；
- 使用项目现有鉴权；
- banned 用户旧 Session 应按现有机制立即失效；
- 用户角色变化后旧权限不能无限继续有效。

### Secret

禁止：

- hardcode `SESSION_SECRET`；
- hardcode 数据库密码；
- 提交 `.env`；
- 提交真实管理员密码；
- 提交管理员安全问题答案；
- 在日志打印 Secret；
- 在文档写真实生产 IP / 凭据。

### 文件

禁止：

- 路径穿越；
- 任意文件读取；
- 用户自己指定服务器绝对路径；
- 未登录直接读取受保护视频；
- 通过静态 URL 绕过权限。

### 日志

可以记录：

- request ID；
- user ID；
- match ID；
- tournament ID；
- storage key；
- error type。

禁止记录：

- 密码；
- securityAnswer；
- SESSION_SECRET；
- DATABASE_URL；
- 完整 Cookie；
- 视频 / 截图绝对磁盘敏感路径（非必要时）。

# 37. 前端安全

不能把前端隐藏按钮当成权限控制。

例如：

- 普通成员看不到“修改战绩”按钮只是 UI；
- API 仍然必须返回 403；
- 蓝队前端不展示红队战术只是 UI；
- 服务器仍必须拒绝访问红队战术数据；
- 路线编辑按钮只显示自己的路线；
- 服务端仍要验证 route owner。

# 38. OCR / 识别模块边界

OCR / 图像识别应被视为：

**不可信输入处理器**

而不是最终数据来源。

模块输出建议包含：

```text
value
confidence
sourceScreenshotType
sourceRegion
warnings
```

业务层负责：

- 合并；
- 校验；
- 玩家推荐；
- 冲突发现；
- 人工确认状态。

OCR 模块不得：

- 直接写正式比赛数据；
- 自己决定谁对应网站成员；
- 遇到不确定值时擅自填 0；
- 擅自修改历史正式数据。

# 39. 文件存储目录

禁止创建：

```text
uploads/phase1/
uploads/phase2/
src/features/phase1/
src/features/phase2/
```

应按业务领域组织。

例如仅作逻辑示例：

```text
storage/
  match-screenshots/
  post-videos/
```

但实际路径应结合当前项目部署方式。

代码层应该通过 Storage Service 使用，不应在业务代码到处拼接绝对路径。

# 40. 清理与孤儿文件

需要处理：

- 数据库写入失败但文件已保存；
- 用户替换截图；
- 上传草稿长期未提交；
- 视频数据库记录创建失败；
- 删除动态后的文件；
- 删除失败重试。

不得出现：

```text
保存文件成功
→ 数据库失败
→ 永远留一个无人知道的孤儿文件
```

建议通过：

- 补偿删除；
- pending 状态；
- 定期清理任务；

实现，具体方式按项目现有基础设施决定。

# 46. 与现有分队算法的关系

本轮新增的战绩与战术功能不能破坏既有分队算法。

必须保持既有核心产品定义：

**先让十个人尽可能玩到自己想玩的分路，再让比赛尽可能公平。**

不得新增：

- 锁定打野；
- 锁定中路；
- 锁定射手；
- 绝对位置；
- 强制位置；
- 玩家位置特权。

战绩中的“实际分路”是**比赛结果记录**，不能反向变成分队算法里的锁位置。

# 59. 最终产品目标

王者演武堂不是只记录一组分队结果。

目标是让每次内战都形成完整的历史记忆：

```text
分队
  ↓
阵容
  ↓
战术
  ↓
内战
  ↓
战绩
  ↓
视频
  ↓
历史回忆
```

本轮第一版优先把：

- 数据真实；
- 权限正确；
- 历史可追溯；
- 原始资料可复核；
- 战术不串队；
- 成员不能替别人画路线；
- 文件不能绕过权限；
- 正式战绩不能被普通用户静默篡改；

这些基础打牢。

不要为了追求“看起来高级”牺牲数据一致性、安全性和现有项目稳定性。
