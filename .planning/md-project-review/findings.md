# 阅读发现

## 项目定位

- Next.js 14 + TypeScript + Tailwind + Prisma 5 + MySQL 的王者荣耀 5v5 内战分队系统。
- 核心域：玩家档案、赛事房间、两阶段分队算法、英雄/装备图鉴、数据同步监控、后台管理。

## 核心架构

- 前后端一体 App Router；API 全部 force-dynamic。
- iron-session + bcryptjs；角色为 admin/user，赛事内另有 owner/co_owner。
- Redis 为 cache-aside 可丢弃缓存，MySQL 是真实数据源，Redis 故障静默降级。
- 英雄/装备从官方数据源同步；cron、监控、SSE 构成自动更新链路。
- `/m` 路由 re-export 主页面，由中间件 UA 307 跳转。
- 双主题由 URL hash 驱动：#1 暗金演武，#2 浅色厚玻璃。

## 核心算法

- 10 人分配至 5 路，每路 2 人，共 113,400 种角色方案。
- 每种方案再用 5-bit mask 枚举 32 种红蓝分队。
- 当前文档中的权重存在版本差异；最新 CLAUDE/AGENTS 口径为偏好优先的四层权重，architecture/spec/technical 又出现 500/350 等不同常量，后续改算法必须以源码和测试为准。

## 风险与冲突

- 文档对默认主题、data-theme 映射、Dock 显示和算法权重存在冲突。
- docs/deploy.md 仍写标准 nginx/certbot 与 8081，根 CLAUDE.md 写非标准 Nginx 路径/acme.sh，部署应优先根文档并核对脚本。
- 安全问题恢复机制仍是审计明确指出的风险；另有安全响应头、canonical、长列表 DOM 等潜在遗留。
- 文档包含远程数据库地址和内置 admin 凭据，后续输出和日志应避免不必要传播。

## 房间与公告增强：工作方法

- 继续使用既有规划目录记录本次多链路变更，当前先审计数据流，再统一设计 API、权限和 UI。
- 弹层层级将使用语义化 token；房间信息优先于成员列表；公告写操作只允许服务端 `admin` 权限。
- UI 校准重点：统一 z-index scale、移动端核心内容优先、弹层提供明确关闭路径和焦点管理、表单使用可见标签及就地错误提示。
- 延期和公告编辑属于复杂表单，采用渐进披露、44px 触控目标、提交 loading/disabled 状态，并保留 reduced-motion 兼容。

## 当前实现审计

- 快速加入接口当前会直接创建成员记录，用户没有查看房间截止时间和公告的确认步骤；应改为“查询预览 -> 用户确认 -> 加入”。
- 公开访客详情接口当前返回完整成员对象，页面也渲染成员列表；访客只需要房间信息、公告、人数统计和加入按钮。
- `CalendarModal` 已支持小时和分钟，但使用 `9999/10000` 任意层级；需要改为 Portal + 统一 overlay/modal/popover/toast token。
- 截止 API 已接收完整 ISO 时间，交互仍以“延长截止”单一步骤呈现；需要明确日期与时间选择、验证必须晚于当前截止时间。
- 公告数据库和 CRUD 已存在，且由 `requireSuperAdmin()` 保护；主要缺口是功能层封装、服务端输入校验、slug 冲突处理、三字段编辑结构及 Markdown 预览。
- 满员判断目前是 count 后 create，存在并发超员窗口；成员增减也没有统一的状态重算服务。
- 成员新增入口包括普通加入、临时补位、临时申请审批；成员减少入口包括主动退出和管理员踢人，必须全部接入统一容量重算。
- 最合适的满员语义是立即把状态切到 `locked`，保留原计划 `deadline`；若人数降到 10 以下且原截止时间仍未到，则自动恢复 `recruiting`，过期房间不会误恢复。
- 日历主遮罩当前没有 Portal，仅时间下拉 Portal 到 body，因此祖先 stacking context 仍可能遮挡主弹窗；应把整个弹层树 Portal 到 body。
- 项目未安装 Markdown 库，已有安全的 JSX Markdown 子集渲染器；可抽为共享功能组件用于公告预览与详情，避免 `dangerouslySetInnerHTML`。
- 现有层级值分散为 30、40、100、1000、9999、99999；统一为 sticky/dock/overlay/modal/popover/toast/transition 语义层级，并让功能弹层 Portal 到 `document.body`。
- 登录找回密码、安全问题、注销账号仍依赖页面内 stacking context；需要一起迁移 Portal，避免只修日历后其他功能继续被遮挡。
- 375px 浏览器回归确认公告编辑、日期时间选择和房间预览均可操作；同时发现日历 key 冲突和 CursorLighting 提前修改 DOM 的 hydration warning，已纳入修复。
- 修复后 375×812 房间预览视觉层级清晰：截止时间、报名情况和公告先于操作按钮，背景正确隔离且弹层未被导航遮挡。

## 全站响应式布局重整：工作方法

- 本轮不把两个关键问题当作孤立补丁：先统一页面壳、栅格、弹层和安全区，再分别核对日历交互与英雄数据链路。
- 视觉修改限定在 `src/web` 与页面组合层；数据完整性和筛选语义需要沿 `features -> core` 追踪，避免仅扩大容器后仍漏数据。
- 回归至少覆盖 375×812、812×375 与 1440×900，并同时检查 `#1`、`#2` 两套主题。
- UI skill 的强制基线与项目要求一致：移动端优先、正文不横向溢出、固定导航预留安全区、触控目标至少 44px、弹层提供明确退出路径并尊重 reduced-motion。
- 全站布局应采用一致的桌面容器宽度和 4/8px 间距尺度；手机端避免嵌套滚动，核心内容先于辅助信息，横屏仍需可读可操作。
- 设计系统检索给出的重 3D/霓虹方案与项目既有“演武暗琉璃 / 浅色厚玻璃”双主题冲突，且性能与无障碍评级较差；本轮只采纳内容优先、层级一致和响应式检查项，不替换品牌主题。
- 详细 UX 检索进一步确认：不能用 `overflow-hidden` 掩盖英雄列表，需提供完整可滚动区域；日历继续使用 Portal 和语义层级，不使用任意大 `z-index`。
- Markdown 明确要求桌面和 `/m` 功能一致、仅布局自适应；个人空间每路最多 3 个已选英雄，但选择器搜索范围必须支持完整英雄数据，不能误解为只展示 3 个候选项。
- 当前 `HeroSelect` 下拉固定至少 280px、固定向下展开且只设 `maxHeight: 320`，没有视口边界夹取或上下翻转；在窄屏/靠近底部时会出屏，形成“英雄展示不全”。
- 当前 `CalendarModal` 仍以 360px 单列和大量 inline style 组织，日期与时间缺乏信息分区；功能正确但桌面空间利用差，移动端也不像原生底部面板，是“不够美观”的直接原因。
- `globals.css` 同时存在主题内移动规则和文件尾全局移动规则，`.main-content` 在手机端先被设置带安全区 padding，随后又被 `padding: 0` 覆盖；这是全站页面边距与 Dock 遮挡不一致的根因之一。
- `RolePreferenceEditor` 的新增行在任何宽度都强制保持“英雄选择 + 80px 战力 + 添加按钮”单行，375px 下会压缩选择器；页脚的“巅峰分数 + 保存”也始终横排，需在手机端改为堆叠。
- `HeroSelect` 当前触发器只有 40px 高，候选项没有 `role=listbox/option` 语义和候选数量提示；本轮需要同时提升触控、键盘可理解性与列表完整性，而不只是修改尺寸。
- 现有页面根容器大量各自声明 `px/py/max-w`，同时 `main-content` 自己再加 24px，形成桌面双重边距、手机被末尾覆盖规则清零的两套不一致行为；应建立共享 `page-shell` 作为唯一页面 gutter。

- 更新日志使用固定 180px sticky 目录并与正文横排，手机端没有折叠规则；装备、英雄及详情同样各自设置根 padding。全站改造至少要覆盖这些高流量入口，而不是只改个人空间。

## 玩家身份与英雄附属分路增强：工作方法

- 本轮涉及 Prisma、服务端权限、功能层和 Web 交互，必须先明确数据所有权和响应裁剪，再修改页面。
- 英雄候选顺序定义为：`roleType === 当前分路` 的主分路英雄在前；`secondaryRoleTypes` 包含当前分路的英雄随后；其余英雄不展示。
- 个人资料编辑、头像更新和登录跳转均需明确 loading/success/error 状态，避免重复提交与重复导航。
- 房间成员敏感资料只对 owner/co_owner 返回；普通玩家仍只获得当前业务所需的最小成员信息。
- UI 检索仍给出与既有双主题冲突且无障碍较差的重 3D 方案，本轮继续保留项目主题，只采纳表单成功反馈、150-300ms 交互、reduced-motion 和明确 loading 状态。
- 登录成功的导航必须由单一状态机控制：认证成功后锁定提交，播放一次动画，动画完成回调直接 `router.replace`；不得同时存在 timeout 和第二次点击入口。
- 头像组件允许覆盖，API 也会更新文件名；“设置后无法更改”更可能是 file input 未清空，重新选择同一文件时浏览器不触发 `change`。上传结束后应重置 input，并补充网络异常处理。
- 当前会话响应仅含站内 `username/avatar`，没有个人资料更新端点；游戏昵称和游戏 ID 需要新增 User 字段、受认证的资料 API，并同步扩展 `SessionUser`。
- 英雄查询只合并 `HeroLaneOverride.roleType` 单一主分路，无法表达附属分路；应新增规范化附属分路关系，由英雄 API 统一返回 `secondaryRoleTypes`，避免前端从展示标签反推数据。
- `/api/heroes/[id]` 的 PATCH 当前只调用 `requireAuth()`，任何登录用户都能修改主分路，和“只有 admin 有权限”冲突；必须改成 `requireSuperAdmin()`，主分路与附属分路在同一事务内校验和保存。
- 赛事详情 API 当前对所有房间成员都返回相同的 `user: { id, username }`；新增游戏身份后必须先判定当前用户是否 owner/co_owner，再按权限构造 select/响应，不能先查询完整敏感字段再原样 spread。
- 管理后台适合在现有英雄表格的分路列中增加“附属分路”多选 chips；主分路不能同时出现在附属分路中，切换主分路时服务端需自动剔除冲突项。
- 登录动画的直接根因是 `GlassShatter` 在 2.5 秒时恢复登录卡片，再等待 600ms 才导航；同时 effect 依赖 inline `onComplete`，父组件重渲染可能重启计时。应使用 callback ref、去掉 settle 阶段，并在 reduced-motion 下立即完成。
- 数据库现有迁移很少且使用手写 SQL；本轮新增独立 migration，保留远程数据库执行边界，只在本地完成 schema validate/generate，不擅自执行远程迁移。
- Windows 下常规 `prisma generate` 因开发进程锁定 query engine DLL 报 EPERM；`prisma generate --no-engine` 可安全刷新客户端类型而不替换被占用的二进制，后续生产构建仍需确认现有 engine 可用。
- `webapp-testing` skill 要求 Python Playwright，但工作区绑定的 Python 未安装 `playwright`；项目自身已安装 Node Playwright 且有既有回归脚本，因此浏览器验证使用仓库依赖的 Node Playwright，不额外安装依赖。
- 当前开发服务连接的数据库尚未执行本轮 migration，不能用真实个人资料查询验证新字段；浏览器测试应拦截认证接口验证登录动画，数据权限通过类型、构建和服务端响应裁剪检查验证。

## 功能恢复：初始约束

- 本轮必须先以 Markdown 和现有官方同步字段确认孙悟空/六耳猕猴的 heroId、命格关系与显示语义，再修改数据过滤规则。
- “补位用户”当前可能复用真实 User 外键，清理必须限定 `TournamentPlayer.isTemporary=true` 且赛事已过期，不能泛化为删除 User。
- 战力四舍五入需分别排查输入控件、API 数值转换、数据库 Int 约束和前端段位公式，避免只改显示层。
- Markdown 的现行命格语义是“孙悟空 ↔ 心魔六耳”：图鉴隐藏命格形态卡，仅本命孙悟空显示双形态徽章，详情页通过 `minggeRelatedId` 双向切换；用户口中的“六耳猕猴”对应文档名称“心魔六耳”。
- 皮肤文档仍依赖 `data-imgname` 和固定 `bigskin-{idx}.jpg`，并只描述 `bigskin-1` HEAD 探测；最新皮肤丢失很可能来自详情页字段变化、只探测首图或 HEAD 被 CDN 拒绝。
- 战力规格明确为“每分路前 5 个战力总和 / 1000”，没有要求取整；UI 若用 `Math.round` 会把 35.499 段显示为 35 或 35.5，必须明确保留的小数精度。
- `sync.ts` 只取第一个 `data-imgname`，皮肤记录只有 `{name,index}`；图片探测只用于英雄封面 `bigskin-1`。`download-images.ts` 又对已存在本地文件直接跳过，因此同索引图片更新或 CDN 规则变化后永远不会刷新。
- 英雄列表以 `herolist.shtml` 的链接为主、JSON 只补字段；若心魔六耳只存在 JSON 或特殊入口，会被合并逻辑直接丢弃。同步目前只检测 `mingge/minggeName`，从未写入 `minggeRelatedId`，图鉴无法加载双形态。
- 图鉴用“所有 `minggeName` 的名称集合”隐藏形态英雄；孙悟空若 `minggeName=心魔六耳` 但关联英雄不在列表，孙悟空仍显示却无法切换；若爬虫误把孙悟空自身识别为形态名，也可能被错误隐藏。
- 战力不准确根因已确认：列表展示把战力先除以 100 四舍五入再乘回去，段位计算也把每个英雄先取整到百位，最终再 `Math.round(total/1000)`，连续两次丢失精度；API 还缺少整数范围校验。
- 代码已有 `scripts/migrate-mingge.ts`，明确配置 `孙悟空 -> 心魔六耳`，说明恢复逻辑应复用确定名称映射并使同步后自动修复关联，而不是要求人工单次跑脚本。

## 2026-07-25 空房间生命周期

- 常规退出 API 明确禁止 `owner` 退出，因此单靠 `/leave` 理论上不会形成零成员房间。
- 创建房间时 owner 同时写入 `TournamentAdmin` 与 `TournamentPlayer`；赛事关联表均配置 `onDelete: Cascade`，直接删除 `Tournament` 可以完整清理成员、管理员、申请与选择记录。
- 用户注销 API 会批量删除其 `TournamentPlayer` 后再删除 User；User 级联删除 owner 的管理员记录，但不会反向删除 Tournament，这是当前可确定的无主 `0/10` 房间来源之一。
- 还需检查踢人和账号注销事务，统一把“成员归零或 owner 消失”的房间作为孤儿房间删除，避免只修 `/leave` 留下旁路。
- 踢人 API 同样禁止踢出 owner，常规退出/踢人后调用的 `reconcileTournamentCapacity` 只重算 recruiting/locked，不处理零成员删除。
- 用户注销使用数组事务：先批量删除其参赛记录和管理员记录，再删除 User；它没有记录受影响房间，也没有删除该用户拥有的赛事，因此 owner 注销会稳定留下无 owner 的空房间或残缺房间。
- 最佳修复是集中提供赛事生命周期 helper：成员移除后若人数为零则删除赛事，否则才重算容量；账号注销时先删除该用户拥有的赛事，再清理其余参赛关系，并对受影响房间执行空房间清理。
- 后台删除用户目前直接 `prisma.user.delete`，同样会留下该用户拥有的 Tournament；两个账号删除入口必须复用同一个事务服务。
- 过期房间任务由 cron worker 调用，适合附带清理历史遗留的零成员赛事；大厅查询仍需添加 `players.some` 防御条件，保证部署后立即不再展示旧 `0/10` 数据。
- 文档原先同时存在“owner 可退出”和“owner 不可退出”的冲突；实际 API 以 owner 取消赛事为准。本轮统一文档，并明确最后有效成员退出、owner 账号删除和历史孤儿清理语义。
